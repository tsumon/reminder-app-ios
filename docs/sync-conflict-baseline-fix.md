# 启动时重复同步冲突：本地修复验收

基线：iOS 2.9.0/build71，`780ea0eb391a45e0909147357c187b71f70e3f12`。
本修复仅供本地审阅：未推送、合并或发布；版本、App/Widget 标识、App Group、entitlements 和 unsigned 工作流不变。Android 未改动。

## 已证实的机制

这不是对用户真实服务器状态的推断。未读取真实提醒、同步配置或凭据，也未替用户选择上传/覆盖。用户此前是否选过一边、是否成功仍未知。

1. `WebDavSync` 用整份远端 JSON 原始字节哈希判断修改。只变化 exportedAt/dataVersion、JSON 排版、已知集合顺序，配合本地修改，就可稳定触发假冲突。相同内容但缺少首次基线时也会要求选择。这段原始哈希判定至少在已发布 2.8.0 中就存在，不能归为 2.9 UI 重构回归。
2. 选择远端并保留本机独有内容时，旧代码在合并结果的条件 PUT 成功之前就写入成功时间/已同步版本。网络失败时，结果与成功基线不一致。
3. 合并后本地内容可能恰好等于旧的本地基线，但仍需回传被保留的提醒。若没有独立的待上传状态，失败后重启会漏掉必要 PUT。

此前 UI 测试的弹窗定位/取消即时可访问性断言问题与以上机制分开处理，本修复没有隐藏或重写冲突对话框。

## 最小修复

- 用持久化的本地/远端内容指纹判断实际数据变化。只在已知协议路径内归一化提醒、历史和墓碑的顺序/UUID 大小写，去重删除标记，忽略导出时钟、计数及提醒的纯 updatedAt 时钟。重试间隔顺序、历史备注、真实墓碑变更和未知字段仍参与比较。
- 真实内容相同可安全建立缺失基线，不导入、不删数据、不写云端。缺少基线且两边内容不同时仍保守询问；旧原始指纹仍作为升级兜底。
- 旧端没有内容基线、计数也未递增时，只有刚下载的远端仍精确匹配已知原始基线，才将内容差异视为本地待上传修改，避免误确认漏增计数的旧数据。
- 保留原始字节/ETag 的选择失效保护、条件上传、选择前快照和幂等历史/墓碑合并。内容比较不会降低网络写入前置条件。
- 将“已消费的远端版本”与“完整同步成功”区分。只在完整成功后确认本地版本、清除待上传标记和更新成功时间；显式选择/持久化合并后的 PUT 失败可在远端未再变更时继续重传。
- 必须回传时，在确认已消费远端之前先记录待上传意图，避免中断后因本地内容恰好未变而漏传。
- 快照捕获的版本和内容一起确认，上传等待期间的新改动仍保留为未同步。只剩本地删除标记时也参与真实双向冲突保护。

## 保护边界

取消不等于解决冲突，不会确认基线或代选一边。真实未解决的双向修改仍会提示；若此前一直取消，这部分提示不会被永久隐藏。远端、ETag 或本地版本在选择期间变化时，旧选择仍被拒绝。断网、解析失败、备份失败、本地拒绝保存和 PUT 失败不标记成功。

这不是在已安装 2.9.0 上远程改数据。实际用户验收需先安装后续包含此提交的构建；本任务没有发布该构建。

## 回归入口

```sh
scripts/check-upgrade.sh
# 也可单独运行编译后的 UpgradeCheck --sync-conflict-check
```

新增检查接入默认 UpgradeCheck，使用合成模型、注入传输和快照存储。重启检查启动同一测试工具的子进程，验证持久化基线/待上传意图；不读取 WebDAV 密码。只读保存失败使用独立临时 SQLite，不是用户数据库。

失败对照、实际运行计数、构建和 UI 结果保存在工作目录 `evidence/sync-conflict-fix/`。红色对照在一次性源码副本恢复旧行为，未修改工作区修复。已有旧回归调整了其独立 fixture：真实修改用于真实冲突测试，空库初拉不继承其他用例的墓碑；没有删除断言。
